# Semantic File Search Design Plan

## Goal and scope

Find files in explicitly chosen folders using natural-language queries such as “the photo of the red bicycle” or “notes about the audio export bug.” Combine semantic matches with filename and extracted-text matches so exact names, identifiers, and terms remain useful.

Keep inference and the index local, make refresh incremental, and preserve expensive embeddings across ordinary moves and renames when their source content is unchanged. Scan only configured roots, not the whole disk.

This extends [Phase 6 — Search](docs/File%20Manager/plan.md#phase-6--search) and must preserve [the existing type-to-navigate behavior](docs/File%20Manager/phase6.md). Semantic search must not delay ordinary navigation or take input from editors and the address bar. The execution defaults below resolve the previous open decisions; numerical limits are initial settings to validate, not measured performance claims. Implementation is in progress; [measured results, deviations and outstanding validation](differences_from_phase_6_plan.md) are recorded separately. This plan does not imply that its acceptance targets have passed.

## Agreed direction

- Use **EmbeddingGemma 2**, initially through **llama.cpp with Q8_0 GGUF weights**, in a local helper process.
- Use **local SQLite** for file records, segments, vectors, and keyword indexing. Begin with exact similarity scoring in application memory; add specialized vector indexing only if measurements justify it.
- Model **files and their segments separately** from the start. Small files may have one vector; long or heterogeneous files may have many.
- Treat the database as a **derived index**. Source files determine what is current; the database preserves expensive derived work and search metadata.
- Keep filenames and paths in lexical ranking. Content embeddings should use content and content-derived titles, so ordinary renames need not change model inputs.
- Combine startup reconciliation, explicit refresh, and lightweight change monitoring while running. Record incomplete scan coverage and unavailable roots explicitly.
- Exclude Btrfs/ZFS snapshot and filesystem-journal integration from this version. Ordinary move reconciliation remains in scope.

## Storage decision and portability

SQLite is the primary storage mechanism for the initial implementation. Keep its working database on local storage even when indexed files reside on a NAS; do not place a shared WAL database on an SMB/NFS share. SQLite's WAL model requires local shared-memory coordination. [SQLite WAL documentation](https://www.sqlite.org/wal.html)

The preference for files carrying their own embeddings remains valid, but portable embedding ownership is deferred. Do not insert embeddings into PDFs or other source documents, or introduce a second authoritative store in this version. Database backup/export preserves generated work using a consistent SQLite backup, as specified below. Rebuilding a lost database may require re-extraction and inference.

**Why xattrs were deferred:** multiple embeddings do not make xattrs technically impossible. Btrfs's usual roughly 16 KiB limit applies to an individual attribute including overhead, and a file can have multiple attributes. ZFS also supports multiple attributes; Linux caps an individual value at 64 KiB, and larger attribute collections can spill out of ZFS's efficient inline storage. A segmented payload could therefore hold many vectors. [Linux xattr documentation](https://man7.org/linux/man-pages/man7/xattr.7.html), [OpenZFS documentation](https://openzfs.github.io/openzfs-docs/Basic%20Concepts/Datasets/ACLs.html)

The reasons to prefer a database here are operational:

- Search would still need a path/vector inventory, with potentially expensive per-file attribute reads to reconstruct it, especially over a network.
- Attribute writes require source-file write access, whereas a separate index can cover readable, unwritable collections.
- Copying, synchronization, and saves that replace an inode may discard attributes; server filesystem support alone does not establish client/protocol support.
- Updating several attributes requires a publication protocol for generations, manifests, interrupted writes, and cleanup. Atomic replacement of one attribute does not make the whole collection transactional.
- Attributes can survive content edits and become stale, so source validation is still required.

This is a complexity and lifecycle tradeoff, not a claim that files cannot own multiple embeddings. Xattrs are not part of the implementation milestones below.

## Indexing scope and eligibility

Users explicitly choose roots and exclusions. Normalize overlapping scopes to avoid duplicate work and results. The initial default skips hidden entries, common generated/cache folders, and configured exclusions. Unsupported content types still receive filename/path inventory. The initial exclusions, format coverage, and resource limits are specified under Execution defaults. Record exclusion reasons rather than silently classifying every omission as an error.

Do not follow symlinks or read special files by default. Reuse the application's existing ordinary-content routing and guarded readers: a regular-file mode alone does not make a pseudo-filesystem entry safe to decode. External extractors and inference helpers must use the project's pinned-input and bounded-process mechanisms where applicable. Do not transplant Recall's unrestricted path-based reads into the application.

Support formats incrementally using existing readers: text and documents, PDFs, images, audio, and video. Recognized ordinary source-code files use the shared bounded plain-text reader and lexical/semantic text pipeline, without executing code or following imports. This extends the original name-only code coverage; generated/cache folders and protected roots remain excluded. Root selection authorizes discovery of eligible files, not unlimited decoding or hashing. Bound work, memory, process count, and per-file extraction, and report when those limits leave coverage incomplete.

## Files, segments, and retrieval quality

Represent each file with zero or more searchable segments. A segment may hold a vector, lexical text, or both. Zero vectors must be distinguishable from successful semantic indexing: a file may be pending, unsupported, failed, or searchable only by name/text.

| Content | Representation |
|---|---|
| Photograph or short text | One segment when it adequately represents the content |
| Long text/document | Bounded passages, retaining offsets or structural locations |
| PDF | Pages or passages, with page numbers; image treatment where text extraction is insufficient |
| Audio | Bounded time windows with start/end times |
| Video | Sampled visual segments and audio windows, retaining times and modalities |
| Recognized source code | Bounded text passages and filename/path search, without execution or import resolution |

Do not force a long file into one averaged vector to simplify storage. A brief topic in a manual or event in a recording can be diluted by averaging or missed by sparse sampling. Use the segment sizes and budgets below, and validate them against representative retrieval fixtures. Report truncation and partial indexing instead of presenting sampled coverage as exhaustive.

Search returns files, preserving their best matching segments for excerpts and page/time navigation. Use the best segment per file and modality, with explicit tests for long-file bias: more segments create more opportunities for an incidental high score. Fuse ranked result lists as specified below rather than summing all segment scores.

An optional whole-file representation may later help group files by overall topic. It would complement segment retrieval, not replace it. Similarity sorting/grouping is a separate feature to evaluate: search vectors provide a baseline, but the model has different text task instructions for clustering and symmetric similarity. Do not assume those tasks are equally well served by the same inputs, or build a full all-pairs similarity matrix for the entire collection.

## Recall compatibility and code reuse decision

**Use our own SQLite schema and indexing/reconciliation implementation. Do not make our database readable/writable by Recall, and do not depend on Recall's complete engine crate.** This is a deliberate compatibility boundary, not a decision to rewrite the inference stack.

The reviewed Recall schema has one path per file row, floating-point timestamps, segment rows attached directly to that file, and index-wide pipeline metadata. Its `Searcher` issues SQL directly against those tables, its `Indexer` directly controls `Store` transactions, and its current migration strategy recreates older schemas. Our requirements add hard-link path associations, root/subtree scan coverage, lossless Linux paths, revision-specific publication, separate availability/freshness, and preservation of embeddings through migrations. Compatibility views or a second Recall-shaped database would add another consistency problem without making that engine satisfy these requirements.

Retain Recall's useful SQLite + FTS5 + segment-vector approach. Reuse code at narrower boundaries:

| Area | Decision |
|---|---|
| llama.cpp C shim, model framing, pooling, media encoder calls | Adapt the reviewed implementation, preserving reference-vector checks; integrate guarded inputs and our helper lifecycle |
| Model manifests/checksums, finite-vector checks, float16 serialization and scoring | Reuse applicable code with focused tests and license attribution; keep our explicit versioning and normalization rules |
| Text splitting and extraction utilities | Reuse pure routines where existing application readers do not already provide them; adapt to token/byte budgets and pinned inputs |
| Filesystem traversal, source opening, external commands, cancellation | Use existing application mechanisms and implement coverage-aware discovery; do not import Recall's path-based I/O wrappers |
| Store/schema/migrations, reconciliation, publication, search SQL | Implement for this plan; port useful ranking/math routines without retaining Recall's table assumptions |
| Recall UI, CLI, watcher, installer and automatic schema resets | Do not adopt |

Record the reviewed upstream commit and MIT notices beside adapted source. Keep this as focused search modules in the shared workbench library plus the dedicated inference helper; configuration and ordinary-content safety stay in core. Do not introduce a general search-plugin framework. Revisit module/crate extraction only if actual sharing or build isolation requires it.

There is no Recall database import/export compatibility requirement in this release. Matching model names alone does not prove interchangeable vectors: extraction, task prefixes, filename titles, precision, and preprocessing must also match. A future importer would need explicit pipeline/source validation; it is not a prerequisite for code reuse.

## SQLite layout and vector representation

Use a versioned schema with logical records for:

- **Roots and scan coverage:** configuration, availability, last completed reconciliation, and incomplete subtrees/errors.
- **Files and paths:** application identifier, observed filesystem identity, exact source timestamps and size (including optional filesystem birth time with an explicit availability flag), current paths, file kind, revision, and indexing state. Allow multiple path associations for hard links; keep identity scoped to the observed filesystem/mount context.
- **Segments:** owning file/revision, modality, page/time/text location, bounded excerpt or lexical content, and vector reference/data.
- **Embedding configuration:** pinned model revision, runtime compatibility identifier, preprocessing/chunking policy, task instructions, dimension, vector encoding, and normalization policy.

Keep related segment/vector/state publication transactional. Use SQLite FTS5 as the baseline for extracted-text and filename search, with filename exact-match behavior handled explicitly. Store bounded segment text/location information for keyword results and snippets using the retention rules below. Do not promise document-content keyword search while retaining neither an index nor a viable extraction path.

Start with **768-dimensional normalized vectors stored as float16**, converted/scored with float32 arithmetic. Q8_0 describes model weight quantization, not the stored vector format. Google's warning about FP16 model inference does not prohibit compact storage of finite, normalized output vectors. Validate dimensions, finiteness, normalization, serialization, and retrieval quality after conversion.

At 768 dimensions, each float16 vector occupies 1,536 bytes. The planning example of 100,000 files averaging 1.5 vectors is 150,000 vectors, or **about 220 MiB of vector payload**. Metadata, text, database pages, WAL, and working buffers add overhead. That average is a workload assumption, not a guarantee: long documents and recordings can require many segments.

Benchmark an exact, blocked CPU scan of relevant vectors before introducing approximate search or a vector extension. Stored vectors do not need to occupy VRAM. Keep a compatible query vector in float32 and avoid copying the whole corpus for each search.

The model supports dimension truncation, but retain 768 dimensions initially as a quality baseline. Any reduction needs evaluation across modalities and matching dimensions/normalization for queries and stored vectors; it is independent of Q8 weight selection.

## Identity, freshness, and publication

Identity answers whether this is the same observed file; freshness answers whether the indexed content is still current. Neither a path nor a device/inode pair is a permanent content identifier.

- Store timestamps at their available integer precision rather than floating-point seconds with a comparison tolerance. Retain relevant identity, size, mtime, and ctime observations. A ctime change is a validation hint, not proof of a content change. Creation-date filters/sorts use observed birth time only; never substitute ctime, first-seen time, or document/capture metadata. Refresh birth-time observations with metadata independently of embedding regeneration, and preserve unknown values.
- Check identity at an unchanged path as well as when detecting a move. Atomic replacement can install a different file at the same name with matching size and mtime.
- Account for inode reuse, hard links, remounts, and uncertain network-file identities. Ambiguity must trigger validation or reindexing, not guessed reuse.
- Use content fingerprints selectively where metadata/identity cannot establish sufficient confidence. Sampled hashes must not authorize reuse. The freshness policy below explicitly states its guarantees and residual risks; do not hash every file on every startup.
- Pin and validate inputs using existing application mechanisms. Recheck source revision and request generation before publishing results; reject work invalidated by edits, replacement, scope changes, or incompatible pipeline changes. A SQLite transaction cannot itself ensure the source remained unchanged during extraction.
- Version pipeline inputs so stale model/preprocessing results cannot silently mix with current ones. Compatible database migrations should preserve valid embeddings rather than force an unnecessary full reindex.

Known-stale vectors may remain stored for recovery, but must not silently rank as current. Distinguish pending, current, partial, stale, excluded, unsupported, inaccessible, and failed states as needed. Indexing failure must not turn an old revision into a successful current result.

## Reconciliation, moves, and unavailable roots

At startup, expose the existing index promptly with its freshness/availability status and reconcile configured roots in the background. Explicit refresh requests a new reconciliation. One blocked or disconnected root must not prevent searching healthy roots.

A crawl must report which directories were successfully enumerated, not just a flat list of files it happened to find. **Not observed does not mean deleted.** A disconnected NAS, permission error, cancelled scan, or failed subdirectory read leaves coverage incomplete. Only completed, relevant coverage can justify retiring unseen path records. Keep unavailable/unverified records for later reconciliation; exclude known-unavailable records by default and offer an explicit offline-results toggle. A root path merely existing does not establish that its expected volume is mounted or that all descendants were readable.

Reconcile same-filesystem moves using verified identity and revision evidence where available. Update path associations without recomputing content vectors. Cross-filesystem moves/copies may require content fingerprints or be treated as new files. Never discard a still-live hard-link path merely because another alias appears. The application's own completed mutations can provide targeted invalidation/move hints, but must retain their existing completion semantics.

Keep mutable filenames and paths out of content-model inputs by default. Use titles derived from file content where available. If a future feature embeds path/name information, version that choice and define the re-embedding consequences of renames. Filename/path keyword records update independently.

While running, use lightweight change notifications to mark affected records dirty and schedule bounded reconciliation. Treat notification loss, overflow, or uncertain coverage as requiring reconciliation. Reconcile remote roots periodically because client notifications may not cover server-side changes. The scheduling and freshness guarantees are defined below. Btrfs/ZFS snapshot and change-journal integration remains out of scope.

## Search and UI behavior

[Phase 6 — Search](docs/File%20Manager/plan.md#phase-6--search) is the authoritative specification for the shared command language, including `:10kb..2MB,image foo`, `:regex:foo.*`, `:emb:"2019 tax document"`, and temporary `:q:...;type:number` columns. This document owns the index and embedding execution behind those commands; do not duplicate the grammar or introduce a separate semantic-query parser.

A leading command colon is intercepted before ordinary type-to-navigate. Commands run on explicit submission, and their metadata/scope constraints apply before candidate ranking and result limits. Only the parsed `emb` payload is sent as the semantic description; name/regex/date/content queries and image dHash sorts must not invoke the embedding model. Literal content search uses verified current extracted text under Phase 6 coverage rules; index tokenization must not silently alter its matching semantics. Bare browser typing retains its existing navigation behavior. Unindexed scope is reported rather than implicitly enrolled.

Question-answer columns are a later Phase 6 capability, outside this embedding runtime's responsibilities. EmbeddingGemma 2 can retrieve relevant segments but cannot return the requested balance/answer itself. A separately validated local answer/extraction worker must provide typed values, applicability, and evidence under the session-only lifecycle specified in Phase 6. Questions/answers are not stored in this SQLite index. The answer-model decision below supplies the starting implementation choice without changing the search/index backend.

### Answer-model and applicability decision

Use two model roles: EmbeddingGemma 2 for semantic retrieval, and one small local generative model for both question applicability and evidence-backed extraction/answering. Do not add a third relevance/judge model by default. The answer worker may use more than one bounded pass with the same weights; a later reconciliation pass must be able to reject conflicting page answers. Replacing the embedding model with a general-purpose generator would sacrifice the dedicated retrieval model without removing the need to build/search the index.

This is a **generic question-answer feature**, not a bank-statement parser or a fixed catalog of document classes. The user supplies the question and requested answer type; each question/file pair gets its own applicability decision. Support extraction, boolean judgments and bounded questions that require interpreting the supplied content. Do not route arbitrary questions through a finance-specific schema, train a bank/non-bank classifier, or make financial terminology an eligibility rule. Bank balances/dates below are illustrative correctness tests, alongside such questions as an agreement's renewal date, a recipe's cooking temperature, whether a document describes an experiment, or an image's depicted subject. Questions that depend on unavailable context or unsupported modalities stay unknown/unsupported rather than receiving an invented answer. Evidence validation must fit the task: literal fields require exact source spans, while interpretive answers require identified supporting passages or image regions and must not be passed off as verbatim extraction.

Evaluate [NuExtract3](https://huggingface.co/numind/NuExtract3) against [Qwen3.5-4B](https://huggingface.co/Qwen/Qwen3.5-4B), initially Q8_0 with bounded context through the existing llama.cpp runtime family. NuExtract3 is a Qwen3.5-4B fine-tune with Apache-2.0 licensing, structured extraction driven by a template plus natural-language instructions, reasoning/non-reasoning modes, and image-to-Markdown support. Its [author-provided GGUF](https://huggingface.co/numind/NuExtract3-GGUF) avoids needing an external conversion provider for that candidate. These capabilities make it a particularly relevant candidate for generic typed columns, not a finance-specific model. Base Qwen remains a useful comparison for arbitrary questions and applicability judgments.

NuMind's roughly 600-document internal extraction benchmark favors NuExtract3 over base Qwen3.5-4B, but this is not a universal accuracy figure: it mixes leaf similarity/exact-match measures, and many Qwen failures were malformed outputs after long reasoning runs. Our short constrained non-thinking protocol differs, and the benchmark does not establish applicability/abstention correctness. The first 20-case local synthetic text check passed 18/20 for NuExtract3 and 20/20 for base Qwen. That initial comparison provisionally selected base Qwen4B. Expanded checks later exposed confusion between literal text absence, omitted facts and negated questions. The application now selects [Qwen3.5-9B Q8_0](https://huggingface.co/bartowski/Qwen_Qwen3.5-9B-GGUF) as its single answer-model default: it passed all 27 expanded synthetic checks on the RTX 3090 CUDA runtime, including the distinctions that both 4B candidates missed. The run took 78.048 seconds overall and its process used 9,216 MiB of GPU memory during a 20-second sampled interval. These are compatibility/quality observations, not a controlled throughput benchmark or an upper bound for every workload. The larger footprint is justified by the observed answer-state correctness; it uses the same role slot and replaces embedding weights while answering. NuExtract3 and base Qwen4B remain development comparisons, not mandatory resident models. This tiny check is not a broad accuracy claim or final acceptance. Choose one answering model after our evidence/type/applicability evaluation, without requiring both in normal use.

The 2026-10-26 decision retains **9B Q8_0**. GPU-unlock improves selected FP16/BF16 compute paths but does not make Q8 weight storage a statement about every arithmetic kernel. Measure actual CUDA prompt processing, generation, per-file model-call counts and peak memory before changing model size or precision. The approved next answering optimization is a restricted, reusable extraction plan, rather than repeated generative extraction for every structured file:

- The same answer model may propose a declarative plan using bounded literal/regex search, nearby text windows, structured-field or table-cell lookup, typed captures and explicit structural checks. These are application-owned operations on already guarded extracted content; no shell, arbitrary Python, network, arbitrary path opening or mutable tool is exposed.
- Keep the plan in the ephemeral column session and reuse it only when each file passes its structural checks. A question alone, filename, extension or similar layout does not prove compatibility. Plan failures fall back to the existing generic answering path, without weakening applicability, evidence or source-lifetime validation.
- Every accepted capture retains exact source location/evidence and uses existing decimal/date/boolean/unit validation. Multiple competing captures remain ambiguous. No match does not prove non-applicability; incomplete search or extraction cannot establish absence or exhaustive totals. Interpretation-heavy and visual questions retain model answering.
- Key plans/results by the question, requested type, plan/prompt version and validated document structure/revision. Never let a cached plan authorize stale answers or leak into another column. Plan generation is explicit column work, with the same cancellation and session lifetime as answers.
- Validate on heterogeneous structured documents, changed layouts, competing labels, malformed/OCR text, missing fields, unrelated files and embedded instructions. Compare direct answering with planning/execution for wrong accepted values, false non-applicability, fallback frequency, model calls and complete-folder latency. A smaller model may later be evaluated for planning, but the current default remains the validated 9B Q8 model. The first implementation now handles bounded YAML/TOML front-matter field extraction; general literal/regex/window/table operations remain planned. See the implementation and isolation details below.


The first implemented plan operation is `frontmatter_field`. It works for an explicit Q/A column on unindexed files, with no implicit enrollment. A guarded reader supplies at most 8 KiB from the selected file, and the isolated interpreter accepts only a complete YAML (`---`) or TOML (`+++`) header within 4 KiB, with bounded scalar fields/paths. The initial mapping call sees field paths and scalar formats, **not field values or the document body**. It chooses a field path through a finite output grammar. That proposal is not by itself permission to accept the answer or reuse it. Existing date validation classifies ISO date/timestamp strings; that format participates in the layout hash, preventing malformed dates from sharing the same cache entry as valid dates. Each column retains at most eight layout-specific plans or refusals in memory. Reuse reparses the current file and validates its selected value/evidence, followed by the ordinary final source-identity check. Changed layouts need a new plan; no match, unsupported values, or an unavailable isolated worker fall back to ordinary guarded document answering. Interpretive questions remain model work. Duplicate metadata keys are rejected; unsupported arrays and unquoted floating literals use fallback rather than silently rounding facts. Unsupported labels remain in the schema; exceeding a path/key/field budget declines the entire fast path instead of hiding possible competing fields.


Semantic review distinguishes literal retrieval from interpretation. Before approving a new mapping, the same Q8 answer model independently answers from the actual bounded header **without seeing the proposed value/path**. Rust validates its evidence and typed value (including units/date precision) and compares it with the extracted candidate. Disagreement or insufficient evidence escalates to full guarded document answering. Agreement then permits a separate scoped review, which sees the actual candidate/header and commits its question scope before its decision: `literal`, `per_file`, or `document`. Only literal field retrieval may authorize reuse; a per-file judgment can accept this row or escalate, and a document-dependent question must escalate. Approving one per-file result cannot upgrade later rows into reusable extraction. Every later literal capture still passes structure/type/evidence/source checks. Each interpretation-dependent capture receives its own independent answer and review.

A sensible first sample is not sufficient to call the question literal: questions requiring per-file plausibility, meaning, negation or comparison stay per-file. For example, asking for a child's actual age needs fresh assessment even when the first age is six, while explicitly asking for the stored age field requests its literal value. Tone/reliability judgments evaluate the relevant content instead of simply reading a stored classification tag. Stored publication-date metadata remains distinct from proof that publication actually occurred. Generic answers also receive explicit instructions to preserve those distinctions; they are never replaced universally with a cached extraction rule.

Escalation is bounded: abandon the proposed capture and use the existing full-document extraction/answering path once, retaining source-lifetime checks and the existing inference budgets. A brief prior-review reason travels outside source evidence, explicitly labeled as unverified analysis to investigate rather than a fact or instruction. It cannot supply a quotation or change the answer type. If the full path still lacks evidence or coverage, preserve unknown/ambiguous/unavailable instead of manufacturing an answer. No new shell/path-opening permission or extra model is introduced. Cached plans and their review policy remain session-only and are invalidated with their column/pipeline. Same-model review is a fallible check, not an independent truth oracle; the quality/abstention gates below still apply.

Extraction execution is a separate data-only process, entered before ordinary application initialization. It requires piped standard descriptors, closes all ambient descriptors, sets resource limits and no-new-privileges, then installs a native-architecture, default-deny seccomp filter **before parsing untrusted requests**. The policy permits bounded memory/computation and pipe transport; it denies opening files, filesystem writes, networking, descriptor duplication, process creation and execution. Standard input must also be a pipe, preventing a writable inherited file from being modified through shared `mmap`. The application owns the source reader and supplies bytes; the model cannot choose a source path, executable or command. If the kernel boundary cannot be installed, the tool does not process its input. Generic answering is still available through its existing guarded readers; there is no unisolated extraction fallback. This does not depend on an inference server offering a sandbox: the existing direct llama.cpp CUDA/Vulkan/CPU helper and Q8 model remain in use.

Validation currently includes kernel denial tests, strict protocol/grammar contracts, duplicate keys and changed source/layout checks, cancellation/cache lifetime, 13 real-model planning cases, 16 composed semantic-review cases, private native date/interpretation/escalation columns and generic fallback, and a guarded check of the 31 Markdown entries directly in the requested Hugo posts folder (30 date values and one missing-date abstention, eight schema-only planning calls in the component probe). These checks do not establish general extraction accuracy for other layouts. Header evidence explicitly says that the document body was not examined; it cannot prove global absence or non-applicability. See [the implementation ledger](differences_from_phase_6_plan.md#restricted-front-matter-extraction--2026-10-26) for retained failures, timing scope and remaining work.

The same isolated plan/review mechanism also accepts a **complete, single-source text document of at most 4 KiB** whose nonempty lines are all unique `label: value` fields. This includes qualifying extracted PDF text as well as plain text. The entire document must meet that structure: repeated labels, prose, empty fields, unsupported labels, incomplete extraction, images, multiple sources and larger documents decline this fast path and retain generic answering. Layout/field kinds select a session-only plan; each capture reparses the current document, retains its original source location and evidence, validates the requested type and performs the ordinary final source check. Schema planning receives labels and kinds without values. This shortcut requires an unqualified request for the exact field, such as “What is the recorded date?” or “What is the stored recorded date field?”. Other questions use complete-source answering. Front-matter optimization likewise admits unqualified field extraction, while contextual questions and judgments use the full source. These checks select an optimization; they do not limit accepted question syntax. The literal mapping still needs semantic review. This is a useful structured-text case, not a general regex/window/table executor or proof that every question has a determinate answer.

The bounded document-field path additionally recognizes literal colon/equal assignments and exactly two-column Markdown or tab-separated rows surrounded by prose. It supplies the entire complete document to the first semantic review rather than presenting a selected row as exhaustive evidence. A template fingerprint includes every non-field line, plus field labels/order/kinds; changing surrounding prose or field structure forces a fresh plan and review, while changing captured values alone may reuse a reviewed literal mapping. Duplicate labels (including case variants across formats) decline this path. It retains the 4 KiB/single-source/no-image limits and explicit unqualified field-question requirement. This improves repeated simple forms without granting the model a shell, filesystem access, arbitrary regex execution or a general multi-column table language. Larger complete text sources additionally use the bounded text-search path below.

Larger complete text documents can use a question-only literal/regex search plan before the ordinary all-window workflow. Reuse the existing unqualified-field parser to add a literal field-label alternative; do not rely on the model to avoid layout/value-format assumptions. Cache only up to 32 question/type/label plans in the answer worker, never per-file applicability or sufficiency. At most three model proposals plus one application label search run in the same isolated byte-only worker. Matching is case-insensitive by default and uses Rust's non-backtracking regex engine with bounded pattern/program/nesting sizes. The worker accepts at most 512 sources/512 KiB extracted text, returns at most eight UTF-8 offset windows of at most 4 KiB each/16 KiB combined, and marks saturation explicitly. The parent slices the original source itself, preserving page/source locations. JSON transport is capped at 4 MiB to accommodate escaping; this does not raise the 512 KiB extracted-content limit. The existing kernel/resource/process-time boundary remains mandatory.

This search is evidence selection, not a trusted answer generator. The same Q8 model answers the selected windows with the existing direct/global/unknown sufficiency basis, then performs a separate per-file review of the question, candidate, executed searches and supplied evidence. Restricted-subject questions decline this partial-search optimization and keep the existing document workflow and its applicability/coverage limits. Missing matches, invalid/limited plans, source saturation, uncertain answers and failed sufficiency reviews fall back to the existing all-window workflow within the same 180-second deadline. A review's bounded reason may accompany escalation as unverified feedback, never as evidence. Selected matches cannot establish global absence, non-applicability, exhaustive totals or that omitted table rows do not exist. The worker also marks a match in a pipe/tab-separated line as requiring table context. Plain text-search plans have no validated row/column selector, so those matches deterministically escalate to the full workflow, even if the model critic would approve a nearby cell. A table elsewhere in the returned context does not block an ordinary prose-field match. Existing small structured two-column field templates remain separate. Faster general table-cell plans would need an explicit bounded row/column selection mechanism; regex matches alone do not supply that authority. Small complete inputs retain the existing full-source answer path; reviewed header/field templates retain their faster literal-capture path. This is a bounded single search/answer/review attempt followed by escalation, not an unrestricted shell or an unbounded autonomous tool loop.

Complete-text answering uses the same Q8 model to separate applicability from fact extraction. First, a question-only pass identifies any restricted subject; it sees no file content. At most 32 such question plans are cached in the model worker. For a restricted subject, a second pass compares the current source with that subject, without seeing the requested proposition/value, answer type or prior candidate feedback. Its verdict and quotations are checked per file; applicability itself is never cached across files. A positively established mismatch returns not applicable, insufficient subject information stays unknown, and an applicable source proceeds to ordinary typed answering. Language, tone and literal-content questions can be unrestricted and retain their existing answer path. Partial sources and selected quotations cannot authorize this complete-source applicability check. No extra resident model is introduced. This separation was needed because both direct answering and a candidate reviewer accepted a misleading imported permission flag in a recipe with the same schema as an agreement. Narrow real-model checks pass, but this remains fallible model inference rather than an independent truth oracle.

Pin the actual converted artifacts, reviewed source/card revision, prompt/template, and runtime support before provisioning; retain checksum verification and explicit downloads. NuExtract3's reviewed GGUF revision is `28a1aae6288c5d50bdf999ca2e572240966d669b`; source/card revision reviewed was `c99dc8f5641b866aa0192b6ea78f84bf9f3535f1`, which alone does not prove the GGUF conversion's exact source commit. Exact artifact sizes/checksums live in `scripts/search_model/answer_models.json`. Use its reviewed structured-task framing, not a plain Qwen chat prompt with renamed weights. Start with current extracted text for readable/OCR'd PDFs. Vision input is an explicit additional path for layout/OCR ambiguity, not an assumption that visual embeddings can answer questions. Do not enable tools, network access, or document-supplied instructions.

[NuExtract 2.0-2B](https://huggingface.co/numind/NuExtract-2.0-2B) remains a smaller MIT-licensed alternative if memory/latency requires it, rather than a mandatory extra benchmark/download now that NuExtract3 is available. Null-for-missing behavior does **not** itself distinguish irrelevant documents from applicable documents lacking an answer. Any candidate must pass the same arbitrary-question, applicability and abstention tests; do not add a third permanent model merely to compensate for an untested prompt. The older NuExtract 2.0 4B variant has a different research license; that does not apply to Apache-2.0 NuExtract3.

[Gemma 4 E2B/E4B](https://ai.google.dev/gemma/docs/core) are reasonable alternatives if the first candidates fail. Their effective parameter labels are not resident weight counts: the [E4B model card](https://huggingface.co/google/gemma-4-E4B-it) lists 8B parameters including embeddings. Compare measured memory and exact-answer quality rather than assuming E4B has the same footprint as a dense 4B model. Do not load all candidates in normal application use. A larger replacement answering model is preferable to a mandatory three-model cascade unless evaluation shows a clear benefit.

Treat the worker response as a discriminated result, not an optional untyped value. Carry applicability (`applicable`, `not_applicable`, `undetermined`), answer status, requested type, raw answer text, normalized candidate, currency/unit or date scope where relevant, source page/segment identifiers, exact supporting quotations and bounded coverage. A not-applicable result carries a reason and supporting observation; it cannot also carry a value. For an applicable boolean question, false is a real answer, never the default for a missing field. Render not applicable as `-`; keep unknown/partial, not found, unsupported, unavailable and failed distinguishable through their cell state and inspection. All non-values sort after comparable valid values in either direction.

Use constrained structured generation where supported, then validate in application code. Verify quoted evidence against the current extracted source and parse exact decimal strings, currency/units, and calendar dates independently. Never accept floating-point money, an ungrounded model confidence, a generated quotation, or syntactically valid JSON as proof that an answer is correct. Evidence matching proves the passage exists, not that the model chose the correct field: opening/closing/available balance and statement date/period end/transaction date need explicit contextual disambiguation. Preserve multiple plausible answers as ambiguous. Do not guess an accounting period from the filename or silently perform unspecified aggregation across accounts/currencies.

Retrieval can prioritize passages within **each** file but cannot decide whether that row deserves an answer. For short statements examine all extracted text within budget; for larger files disclose which pages/segments were examined. Failure to retrieve a passage or exhausting a budget leaves applicability/answer undetermined or partial, not not-applicable or a definitive absence. File-type metadata can establish an unsupported path, but cannot universally prove irrelevance (a statement screenshot is an image). Classify clear unrelated content as not applicable only when supported by the examined material. Cache completed results only in the window's memory against current source revision and worker version; the answer path must also work for explicitly queried unindexed files through guarded readers.

Current text implementation keeps the direct path for small complete inputs and uses the same answer model for bounded evidence selection/reconciliation on larger inputs. Extraction admits 512 KiB/512 sources; inference examines up to 64 overlapping 8 KiB windows with a 180-second overall budget. Retain at most 64 exact quotations/24 KiB, preserve source locations, and abstain on saturation or incomplete extraction. Selected quotations can establish directly supported facts but cannot alone establish exhaustive totals, whole-file absence or non-applicability. Those larger-document global cases remain limited; see [the implementation ledger](differences_from_phase_6_plan.md#bounded-hierarchical-text-qa--2026-10-21) for current checks and limits.

Still-image Q/A now uses the same Qwen3.5-9B weights with its matching pinned f16 projection, loaded lazily in the existing answer role. Explicit answer-model setup acquires the projection; text-only use keeps working without it. Guarded readers prepare bounded PNG pixels, and the answering worker receives bytes rather than source paths. Responses cite normalized image regions and short observations, labeled as model interpretations in the cell tooltip. Validate the type/state and region bounds independently, but do not call this verified OCR or confuse region validity with factual correctness. A six-case synthetic protocol check and private native columns in both themes pass; broader visual accuracy remains unproven. Bounded short/scanned and mixed text/image PDF handling is now implemented through page evidence selection and shared reconciliation; native synthetic checks preserve both pages of a conflict and find a late scanned-page answer. Dense text pages still use extracted text rather than automatic visual/layout analysis. Full details and retained failures are in [the implementation ledger](differences_from_phase_6_plan.md).

For mixed PDFs, collect at most 512 page/source parts, 512 KiB text, 16 images and 16 MiB encoded image data. Use the existing source reader's sparse-page rule (fewer than 200 non-whitespace extracted characters) to choose visual pages. A single visual page can be answered directly. Multiple pages use question-specific evidence selection, then reconcile all retained candidates with page identities preserved. Already selected visual evidence enters reconciliation directly, avoiding redundant selection. Keep the read-admission deadline and per-helper bounds, and share a 180-second inference deadline across visual selection, text selection and reconciliation. Insufficient coverage or saturated evidence remains unknown/partial. Selected observations cannot establish global absence or non-applicability, and region validity does not prove that the model read a field correctly.

Acceptance covers diverse synthetic documents and mixed media with arbitrary user questions: agreements, recipes, technical prose, tabular records, pictures, and statements, with known numeric/date/text/boolean answers, valid false/zero, missing fields, non-applicable files, and unsupported modalities. Include negative/localized numbers, units/currencies, competing labels, multiple plausible values, date ambiguity, OCR damage, truncation, and embedded instructions. A file can be non-applicable to one question and applicable to another. Measure wrong-value acceptance and false non-applicability separately from answer coverage, plus latency and peak VRAM on the RTX 3090. Review evidence/field correctness as well as schema validity. No model is accepted solely on its general benchmark or its own confidence. Limit the initial context rather than allocating the advertised maximum; the answering helper loads on demand, yields to interactive search, and releases idle weights. Coordinate its GPU budget with the embedding helper so the two roles do not imply uncontrolled simultaneous residency.

Use the model's search-query and document task instructions; no code-search mode is included in this release. Rank using both semantic and lexical evidence. Exact filenames, IDs, and technical terms must remain useful when semantic scores are weak. Use reciprocal rank fusion with the specified lexical weight; raw lexical and cosine scores are not directly comparable.

Result activation must retain the captured source observation through deferred studio reads, rather than checking only the click. When an edit creates an owned working file, retain its identity/lifetime with queued operations and undo snapshots; restoring the original must restore its original guard. Use pinned input handles and owned staged outputs for transformations. Channel edits and range deletion share the guarded working-file pipeline. Explicit audio editor handoffs render a checked session copy off-thread, preserve current effects, and retain accepted copies independently of the viewer so forwarding/daemonized editors can open them. These copies are separate from source files and the semantic database. Stem preparation normalizes a checked source and passes pinned prepared-input/output-directory descriptors to the Demucs tensor API; completed stem previews own their derived files and read checks. Grouped playback loads and revalidates its complete audible batch off-thread, while stem exports share the accepted audio-save completion guard and use pinned inputs/destinations with atomic no-overwrite installation. Multi-stem editor handoffs share the checked session-copy worker, revalidate the complete batch, preserve current per-stem edits, and retain independent named copies/profile after launch. Accepted editor copies are temporary working artifacts retained until external/manual/system temporary-file cleanup; do not automatically sweep them or infer editing completion from launcher exit. Failed/cancelled preparations clean immediately. The UI reports that a session copy was opened; users save permanent results through the external editor. This deliberately favors preserving forwarded or unsaved external edits over bounding storage after explicit handoffs. Other follow-up is recorded in [the implementation ledger](differences_from_phase_6_plan.md).

Show file results with useful matching segments and preserve browser selection, history, and navigation behavior. Do not invent a page/time explanation from an aggregate vector. Show partial coverage and last verification age. Known-stale semantic results are excluded; offline results are opt-in.

Keep filename and keyword search usable while the model is loading or unavailable. Cancel obsolete query work and reject late results for a different query/scope. Prioritize interactive query work over bulk indexing so an initial crawl does not make search unusable.

## Runtime, precision, and reuse

Run a bounded, managed helper using llama.cpp's direct multimodal interfaces where the generic server endpoint is insufficient. Keep model downloads explicit and version-pinned; queries and file contents remain local. Reuse existing application subprocess, cancellation, ordinary-content, and media-extraction mechanisms.

Recall is a useful Rust reference for SQLite/FTS, segments, compact vectors, and helper integration, but its reconciliation shortcuts are not the correctness specification. In the reviewed checkout, same-path checks omit replacement identity, timestamps use floating-point/tolerance comparisons, and failed subtree enumeration can be confused with deletion. Adapt reusable code to the requirements above and retain applicable license notices.

Distinguish the model's advertised capabilities from a wrapper's actual limits. The model card specifies an 8,192-token context; the reviewed Recall wrapper uses 2,048 indexing tokens and 512 query tokens. Use the explicit context and segment limits below, and test framing/token accounting rather than inheriting a wrapper's truncation behavior accidentally.

Treat prior estimates of roughly 1 GB for the full runtime and 250 MB for text-only as rough planning figures, not measured RTX 3090 VRAM usage. Download sizes and comments do not establish resident or peak CUDA allocations. Measure cold loading, warm queries, representative media indexing, and concurrent query/indexing behavior on the actual backend.

Q8_0 is the starting choice to reduce weight memory. Its speed relative to BF16 is workload/backend dependent. Validate retrieval quality as well as numerical agreement with a BF16 reference; nearly identical vectors can still change close rankings. Use supported BF16/FP32 inference for that reference, not FP16 model inference.

Use CUDA by default on supported NVIDIA systems, with Vulkan and then CPU fallback, one embedding inference helper, and a five-minute idle release. Benchmark the available backends and verify text-only/media loading as described below. Avoid duplicate model instances and prioritize queries between indexing batches.

## Execution defaults

These choices are the implementation baseline. Persist user-facing choices through the existing configuration writer under `[file_manager.search]`. Roots are individually enrolled/removed, and exact path exclusions control individual files/subtrees. Hidden-content eligibility and the disk/vector quota are catalog-wide preferences, independent of browser visibility. Overlapping roots share vectors, so a per-root physical-storage quota would have ambiguous ownership and could charge the same embedding twice; use one accounted catalog budget. A single hidden policy likewise avoids overlap-dependent eligibility. The tradeoff is that roots cannot independently override those preferences; subtree exclusions remain available. Pipeline-affecting settings change the relevant pipeline fingerprint and queue affected files; scheduling/UI changes do not re-embed content.

### 1. Eligibility and indexing budgets

- Start with no indexed roots. Adding a root explicitly enables its metadata inventory and supported content indexing while the file manager is running. Nested mounts are excluded unless separately added as roots. An explicitly chosen symlink root may be resolved once to a verified ordinary directory; do not recursively follow symlink entries.
- Inventory names and paths of ordinary entries even when their content type is unsupported. Directories have no embeddings. Exclusions remove subtrees from both inventory and content indexing; overlapping roots retain membership independently so removing one does not remove another's coverage.
- Skip hidden descendants by default, independently of the browser's Show hidden preference. The root itself is allowed even if its name starts with a dot. Default excluded directory basenames: `.git`, `.hg`, `.svn`, `.cache`, `.venv`, `venv`, `node_modules`, `bower_components`, `__pycache__`, `site-packages`, `target`, `build`, `dist`, `coverage`, `DerivedData`, `Pods`, and `Carthage`; also skip `*.noindex`. These generated/protected exclusions cannot be overridden by enrolling a root or enabling hidden indexing. Do not skip entire code projects or guess that large media folders are datasets.
- Text-content support: TXT/TEXT, Markdown, RST, ORG, HTML, RTF, DOCX, ODT, PPTX, and XLSX through available guarded readers. PDF is separate. Media formats use core's existing image/audio/video classifiers and decoder support, including embedded RAW previews. Do not add independent extension lists for media. Recognized source-code formats share the bounded plain-text content pipeline without execution or import resolution. Archives other than supported office containers, executables, 3D files, and MIDI receive name/path indexing only in this release.
- RTF uses core's native `rdocx` byte reader inside the owned source helper, without launching an office renderer or resolving fields/links. It extracts accepted body paragraphs/table cells, with the same 64 MiB source/8 MiB text budgets. Any conversion diagnostic, omitted embedded image or text truncation makes coverage partial. Headers, footnotes, objects and field results that the native reader skips are not silently treated as searched; incomplete extraction cannot supply a definitive Q/A value or non-applicability decision. Malformed/over-limit input fails explicitly. RTF preparation has a 30-second outer operation limit and 20/25-second CPU limits; cancellation still kills/reaps its owned reader.
- Do not index credential/key material by content: default-deny `.env`/`.env.*`, SSH private-key basenames, and PEM/KEY/P12/PFX/keystore files; exclude `.ssh`, `.gnupg`, `.aws`, and `.kube` descendants even if hidden indexing is enabled. Ordinary user exclusions can be edited; protected-content routing cannot be bypassed by search settings.
- Missing extractors, encrypted documents without available plaintext, unsupported encodings, and unsupported decoders retain filename search and a reason. Do not install tools automatically or fetch HTML resources. Automatic OCR/transcription is deferred: visual PDF pages can be embedded without inventing an OCR text index, and audio is searched through its audio embeddings.

| Budget | Default behavior |
|---|---|
| Text/document input | At most 64 MiB source and 8 MiB extracted UTF-8 text; oversized supported inputs remain name-only, bounded extraction is marked partial |
| PDF source/pages | At most 512 MiB source; first 512 pages; page/segment limits produce explicit partial coverage |
| Image source | At most 256 MiB; reuse the existing raster/pixel limits and bounded thumbnail path, with no RAW development |
| Audio/video source | At most 64 GiB per file; audio coverage limited to the first two hours; visual video samples may span the full duration |
| Segments | At most 2,048 segments per file, across modalities; record completed locations and the limiting reason |
| Extraction work | Two active jobs globally, at most one per remote root; 30 seconds per document/page/frame operation and 60 seconds per audio window, with existing cancellation/child ownership rules |
| Staged data | At most 256 MiB for staged content: two retained file-job reservations of 64 MiB each, leaving headroom for two bounded reader transports and one inference request. Prepared replies admit at most 8 MiB text/16 MiB encoded media and bounded repeated metadata; cached/resumed segments are bounded before owned allocation. Metadata inventories, vector caches and model weights have independent budgets. |
| Index storage | 10 GiB soft budget including database/WAL/staging, plus 1,000,000 vector limit; pause new content work at the limit and show the reason, preserving search and existing data |

The catalog disk/vector quotas are configurable indexing settings. The per-file byte/page/duration/segment caps are bounded reader policy constants, with partial/name-only coverage and reasons exposed rather than silent truncation. Do not offer an unrestricted per-file limit knob before the worker memory/time admission can safely account for it. Model files are separate from the index quota and their download size is shown. Enforce admission with room for the next bounded write; an unexpectedly growing WAL or disk-full error pauses indexing safely. Do not automatically evict valid embeddings to make room for new ones.

### 2. Segmentation and model inputs

- Split text at paragraph/sentence boundaries when possible, targeting at most 768 model tokens and 8 KiB UTF-8 per passage, with up to 128 tokens of overlap. Hard-split when a single paragraph exceeds the budget. Preserve original offsets; normalization must not corrupt excerpt locations. Include at most 128 tokens of a content-derived title; use `title: none` otherwise.
- For PDFs, keep page locations and split dense text pages into passages. If fewer than 200 non-whitespace characters can be extracted from a page, create a bounded visual-page segment as well, retaining any useful text lexically. Count Unicode non-whitespace characters, excluding layout padding. The PDF decoder representation versions this page-selection rule so an upgrade revisits PDFs without invalidating other decoders; exact compatible canonical vectors remain reusable. Avoid an unconditional text-plus-image duplication for every text page. Record page coverage and unsupported extraction explicitly.
- Use one image segment per ordinary image, with 280 vision tokens. Use the same 280-token budget for visual PDF pages and 140 for sampled video frames. Follow the pinned processor's resizing/normalization behavior; existing image readers supply safely decoded input, not arbitrary UI-rendered crops.
- Audio: mono 16 kHz input, 30-second windows with a 25-second hop. Include the final short window; merge a final tail shorter than two seconds into the preceding window when available. Do not filter quiet windows with an unvalidated silence heuristic. Store exact represented time ranges.
- Video: one frame every five seconds, capped at 1,024 frames. For longer videos, sample uniformly over the full duration instead of taking only the beginning. Use one representative frame for clips shorter than five seconds. Also index the audio stream under the audio-window policy. Frames describe observed instants, not all intervening motion; label visual coverage as sampled.
- Keep source locations outside the model text unless they are part of meaningful content. Store a SHA-256 of the canonical model input plus pipeline fingerprint for each segment. This allows identical segment inputs to reuse a vector after re-extraction without using the mutable filename as a title.
- A limit-truncated file is `partial`; a video sampled according to its declared policy has `sampled` coverage. Neither is described as exhaustive content understanding. Changing segment/sampling policies creates a new pipeline version.

### 3. Freshness and reconciliation contract

- Use exact size, nanosecond timestamps where supplied, ctime, and verified filesystem/object identity for fast reuse. Unchanged observations under a verified root can reuse stored segments without reading payloads. This is best-effort freshness for ordinary filesystem changes, not proof against an actor restoring metadata or an uncooperative server hiding changes.
- Compute a full SHA-256 during initial/replacement indexing of sources up to 64 MiB. If a later metadata-only change or uncertain move has the same full digest and pipeline, reuse its segments and update observations. Reuse the project's existing SHA-256 dependency.
- For larger files, do not perform a separate full read merely to hash them. Use observed identity/revision for the unchanged fast path; on uncertainty, re-extract bounded segments and reuse vectors only when canonical input hashes match. Sampled source hashes never establish content equality. External moves of large files during downtime can therefore require extraction even when inference is avoided.
- Verified completed application moves and reliable paired move notifications can update paths immediately after identity/revision checks. An unpaired move, reused inode, changed mount session, or unknown identity requires reconciliation. Retain all live hard-link paths.
- Debounce local dirty-path events for one second. Reconcile local roots at startup and every 30 minutes while running as a backstop; reconcile remote/unknown roots every five minutes. Do not overlap crawls of the same root. Unknown watcher coverage or overflow schedules a root reconciliation immediately; queue delays and scan duration are visible, so these intervals are targets rather than a hard freshness SLA.
- Probe unavailable roots in bounded helpers with backoff of 30 seconds, one minute, two minutes, then five minutes. No UI-thread filesystem calls or indefinitely blocked worker slots. Remote calls that remain blocked keep their admission slot until the owning child actually exits; health failures must not spawn unlimited replacement helpers.
- A failed or cancelled directory enumeration cannot authorize deletions in that subtree. To remove an unseen path, require complete relevant enumeration, the expected mounted source, and a final bounded absence check. If a formerly indexed directory is now absent, confirmed absence of that directory can retire its descendants without enumerating nonexistent children. Defer retirement when evidence conflicts or coverage is incomplete.
- Cached records awaiting startup verification may appear immediately with `Checking` and their last verification age. Known-stale embeddings are excluded from semantic ranking; offline/inaccessible records are excluded unless Show offline results is enabled. That toggle exposes last-known content with an unavailable label, never as current. Partial but current segments remain searchable with their coverage label.
- Scope/model/source generation checks apply at query publication and action time as well as during indexing. Revalidate a result before opening/revealing it; do not follow an obsolete path to a replacement file on the assumption it is the indexed object.

### 4. Schema, retention, and recovery

Use `rusqlite` with bundled SQLite/FTS5, WAL, foreign keys, a single background writer, and short read transactions. Default to `synchronous=NORMAL` for this rebuildable index; a power loss can lose recent work, so pending jobs are reconciled on restart. Keep vector/text publication in one transaction, never a separate vector file whose revision can drift from its rows. Root settings live in the existing config; database root rows mirror their stable configuration IDs and runtime observations, rather than providing a competing configuration authority.

| Logical table | Required role |
|---|---|
| `roots` | Root configuration reference, stable source identity where available, availability and last coverage time |
| `scans` / `scan_directories` | Scan generation, per-directory completion/failure and membership needed for conservative retirement |
| `files` | Stable application file ID and scoped observed object identity; no single-path uniqueness constraint |
| `paths` / `root_paths` | Lossless native path bytes, searchable display name, parent association, root memberships and last-seen scan |
| `revisions` | File ID, exact source observations, optional full digest, pipeline, state, coverage and publication generation |
| `pipelines` | Full model hashes/revision, effective preprocessing/prompt/chunking/encoding settings and compatibility version |
| `segments` | Revision, kind/modality, integer page/offset/time location, canonical-input hash, text and optional vector blob |
| FTS tables / schema metadata | Separate path/name and segment-text indexing; explicit schema version and transactional migrations |

The implementation also keeps an optional `file_checkpoints` table for interrupted indexing. After eight newly completed segments, append the batch and its extraction/text cursor in one transaction following source verification. Partial rows remain labeled incomplete and keep the folder building state; matching source revision/scope, pipeline, extraction version, dispatch format and available full digest are required before resuming. An intra-text cursor additionally verifies the regenerated prepared text hash and its UTF-8 boundary. Unknown source continuity requires fresh extraction, retaining only canonical-input vector reuse. Finalization preserves the committed prefix's IDs and float16 bytes instead of requantizing them. Backup imports retain canonical segments but deliberately discard cursor hints and reverify sources. See the [durable-checkpoint implementation checkpoint](differences_from_phase_6_plan.md#durable-partial-indexing-checkpoints--2026-10-26) for validation and limits.

Store Linux paths as bytes with a separate display/search representation; never round-trip identity through lossy UTF-8. Use integer pages/offsets and integer microseconds for media times. Maintain explicit scope/revision joins in every search query; old/staging/inaccessible rows must not leak through a bare FTS join.

- Store only the bounded text actually indexed per segment, plus locations; derive a display excerpt of at most 512 characters. Do not retain full decoded media, PCM, page rasters, or extraction scratch after its job finishes. Keep temporary files under the application-owned cache directory with pinned cleanup.
- Publish completed segment batches for a verified source revision as partial results, recording coverage. A changed source invalidates all batches of that revision. Once replacement publication succeeds, delete superseded rows; retain an old stale revision for hash reuse for at most seven days. No unbounded historical embedding versions.
- Retain only the current scan, the last successful coverage needed for reconciliation, and current failure summaries; prune superseded scan-detail rows after reconciliation so periodic scans do not create unbounded history.
- Keep offline records until their root is removed or the user clears them. Removing a root immediately removes it from query scope, then deletes records no remaining root references. Clear index deletes all derived records and scratch while retaining configured roots/model files. Both actions use the application's normal explicit destructive-action UI.
- Place `index.sqlite` under `$XDG_DATA_HOME/little-screen-clip/search/` (default `~/.local/share/little-screen-clip/search/`). Respect the existing application path resolver and require supported local index storage: Btrfs, ext2/3/4, XFS, ZFS, F2FS, bcachefs, tmpfs (volatile), or overlayfs. Reject network, FUSE and unknown filesystem types before opening SQLite; a network denylist cannot establish locality, and FUSE may be remote. This deliberately excludes some otherwise local FUSE/unknown implementations from hosting the live index. Set `XDG_DATA_HOME` to a supported local location for the Files invocation to override its location. Explicitly indexed source folders may still be on ordinary remote/FUSE data mounts; this hosting restriction applies only to the live catalog, not source eligibility or exported self-contained backups. Do not silently fall back to a network WAL database. Use private user permissions for the directory and database.
- Reuse free SQLite pages. Run passive checkpoints during normal operation and bounded idle checkpoints after readers release snapshots; do not hold a read transaction throughout model inference. Make compaction an explicit maintenance action, not an automatic full rewrite after every deletion.
- Migrations preserve compatible rows transactionally. A newer unknown schema disables this feature with an explanatory error, rather than deleting/recreating the database. Pipeline updates retain schema/data but queue only affected revisions; incompatible old vectors are hidden from the new query encoder.
- Backup/export uses SQLite's online backup mechanism to produce one self-contained `.sqlite` snapshot, including schema/pipeline metadata and roots but excluding model weights. Never copy only the live main file and omit its WAL. Restore validates schema/integrity into staging, replaces the closed index atomically while retaining the previous copy until success, and marks restored roots unverified. Restore/import accepts our format only; Recall import is deferred.

### 5. Runtime, scheduling, and resources

- The file manager owns the coordinator, SQLite writer, and helper lifecycle. Indexing runs while it is open; there is no new always-running daemon. On exit, cancel reads/inference, settle any short accepted database transaction, kill/reap owned children, and resume pending work on the next launch. A second process must not independently write/index the same catalog; use a per-index ownership lock and report the existing owner.
- Start from Recall's reviewed llama.cpp `b11461` integration, including review of its embedding-only logits-allocation patch. Pin the resolved source commit and patch hashes in the build manifest. Use `ggml-org/embeddinggemma-2-GGUF` revision `bfcd298762cc34d0357ece5ebdd31791a3a374d8`, Q8_0 text and media files, with the SHA-256 checksums from Recall's reviewed manifest. A failed compatibility/quality gate requires a documented pin change, not an automatic latest-version download.
- Build CUDA, Vulkan and CPU support when their toolchains are available; try CUDA, then Vulkan, then CPU in fresh owned helpers. Report the backend actually selected. Keep one embedding helper/model instance: prioritize interactive requests between indexing batches and pause background inference while queries are pending. No second resident embedding copy for queries.
- Set an effective 2,048-token indexing context and a 512-token query limit, including framing. This deliberately bounds work below the model's maximum; passage segmentation covers long text. Reject an overlong query with a clear length message rather than silently truncating it. Never truncate media inputs silently to fit a wrapper.
- Admit up to four prepared text segments per inference batch only when their total framed tokens fit the 2,048-token batch budget; use one media segment per request. CPU fallback uses at most four compute threads. Two extraction jobs can prepare inputs, but the bounded queue applies backpressure instead of accumulating work.
- Prefer visible/current-folder jobs, then round-robin roots. Give a long file at most eight segments before yielding to another file; retain checkpoints. Queries bypass that background queue, obsolete query results are discarded, and helper stalls are governed by bounded timeouts (10 seconds per warm query, 60 seconds per indexing request, 120 seconds for initial model load). Kill/reap on expiry; do not overlap recovery with a still-live previous helper.
- Load text-only for query/text work when possible; upgrade to media support when needed. Keep the loaded model while work continues and release after five idle minutes. Persist a Keep model loaded option, default off. Do not unload/reload between individual files.
- CUDA initialization/OOM failures advance through Vulkan and then CPU, once per backend for the affected load/job, with a visible status. Retain the successful backend for the loaded session. Other bad-file/model failures are recorded; do not retry indefinitely. Automatic transient file retries use one-minute, five-minute, and 30-minute backoff, then wait for change/manual retry.
- Cap the in-memory vector cache at 512 MiB, including conservative lookup/allocation overhead. Lazily retain normalized float32 working copies of admitted float16 vectors; keep SQLite as the canonical store and evaluate current scope, visibility, policy and metadata constraints on every request. Invalidate on connection writes or SQLite data-version changes, explicitly invalidate for backup-API restore/clear, and reject results if the database changes during retrieval. Cached rows use a derived covering lookup index to avoid materializing their canonical BLOB again. When the cache fills or allocation fails, continue uncached exact scoring from SQLite with bounded buffers and cancellation; scope is not silently reduced. Refresh in place or release the old allocation before growing, without a second full matrix. Release vector buffers after five minutes without vector queries, independently of the Keep model loaded option. Large-scope progress and final operational acceptance are tracked in the implementation ledger.
- The standalone runtime probe now measures CUDA/Vulkan/CPU text-only and media-capable Q8 helpers, including near-context batches and maximum prepared audio windows. The 3090 measurements meet the following steady embedding-VRAM target; controlled private-copy/mincore runs verify model-file page-cache-cold startup separately from physical/system cold. See the work ledger for actual medians/p95 and RSS/GPU scope. The frozen production retrieval check now passes all nine CUDA/Vulkan/CPU index/query combinations with identical request hashes and unchanged product floors; some lower-ranked alternatives differ, without expected-file rank or recall loss. This supports backend-independent vector reuse on those fixtures; broader representative quality remains separate.
- Aim for at most 2 GiB steady model VRAM on the 3090 with these settings, but measure peak/runtime use and report actual consumption. This is a validation target, not a promise of enforceable GPU allocation limits. If it cannot be met, reduce batching and document measured results before changing the memory target or adding a new backend.

### 6. Search UX and ranking

- A leading `:` is the primary command entry; ordinary typing outside search retains type-to-navigate. Retain Ctrl+F as an optional context-aware entry to the same draft bar from the file list, an unfocused browser, or that search field. It does not submit a query or load a model. Editors, address/tree/media focus and Constellation's own find shortcut retain their handling. This follows the Phase 6 document's ownership of command interaction rather than imposing a separate entry policy for semantic queries.
- Default command scope is Current folder (immediate entries, plus inline-expanded entries when supported); offer Recursive and All indexed folders as explicit scope choices, plus a root selector. Use the Phase 6 scope rules rather than silently including all descendants. Search never adds a root implicitly. In an unindexed current folder, offer current-list filename matches and an Index this folder action; do not silently start recursive content reads. All indexed folders remains available.
- Provide a Meaning control as a visible editor for the shared `emb` query mode: it inserts/removes the explicit operator while preserving compatible selectors and scope. Do not let a persisted toggle silently turn plain browser typing, a name command, or a regex command into semantic search. During an explicitly submitted embedding query, filename/FTS candidates may appear while its model loads. The first explicit semantic-use/indexing setup offers the pinned model download; ordinary type-to-navigate never triggers it.
- Add Edit → Search settings for roots, exclusions, Pause indexing, Refresh index, model residency, limits, backup/restore, and Clear index. Advanced budgets can use the existing settings/config pattern rather than adding controls to the browsing toolbar. No additional top-level workbench tab.
- Commands execute on Enter according to Phase 6; do not run embeddings or answer extraction while a command is incomplete. Debounce changes by 150 ms only for a non-command live-search UI. Show up to 100 files initially, with explicit Load more to a 500-file retrieval window; indicate the cap. Freeze the selected file by stable identity while late semantic results arrive; do not silently move keyboard focus to a different file.
- Search results use the existing list/viewer mechanisms, with path, match snippet/location, and coverage/availability status. Enter in a command draft submits it without opening a file; Enter on a subsequently focused result or double-click opens the selected file through existing behavior; Reveal navigates to its parent. Escape closes search and restores the prior browser location, selection, and scroll. F5 in search refreshes the current search scope; outside search it retains ordinary directory refresh.
- Parse the shared Phase 6 syntax before invoking retrieval. Metadata selectors and scope are hard constraints; apply them before scoring and component top-N limits. A name command follows exact/prefix/substring ranking, and regex has its own explicit semantics, without FTS or semantic fallback. For the lexical component of an embedding query, treat the parsed payload as literal text rather than raw FTS syntax: tokenize/escape, use AND between terms, a prefix on the last token of at least three characters, and an OR fallback only for short keyword payloads of at most three tokens when there are no lexical matches within the same hard constraints. Full natural-language descriptions keep the stricter AND pass: broad incidental-word matches were measured to crowd out strong cross-modal results. Use FTS5 `unicode61` with combining marks included and diacritic removal, without English-only Porter stemming. Preserve originals for display.
- For embedding result ranking, rank case-sensitive full-basename matches first, then case-folded full-basename matches. Ordinary navigation and explicit name commands instead retain Phase 6's case-insensitive exact/prefix/substring tiers and display-order ties. For remaining results, build one lexical list (filename prefix, filename substring, then FTS rank) and one semantic list per modality. Each semantic list ranks files by their best matching segment; keep up to three matching locations for explanation. Never reward a file by summing all of its segment scores.
- Keyword scans may reject a row before expensive SQLite membership checks only when the current request's existing Top comparison proves it is already dominated by fully admitted candidates. This is not a postings cap or cached eligibility: all surviving rows still receive complete scope/source/session/policy/metadata checks, retained paths still merge matching locations, and natural-name ties remain exact. Keep the mutable predicate scoped to that lexical pass and remove it on success/error.
- Fuse with reciprocal rank fusion: full-query lexical contribution `2 / (60 + lexical_rank)`; semantic contribution `(1 / M) / (60 + modality_rank)` for each of the `M` modalities searched, using one-based ranks and zero for absent ranks. When the lexical list exists only because the short-query OR fallback ran, use `(0.5 / max(1, M)) / (60 + lexical_rank)` instead: matching only one word is weaker evidence than matching the full query or a semantic modality. Keep those partial matches available without letting common words crowd out cross-modal results. This weighting does not discard stopwords or change literal content/name queries. This reserves total semantic weight 1 irrespective of modality count and avoids directly mixing cosine and BM25 scales. Retrieve up to 500 files per component before fusion; break ties by the existing natural filename comparator, then lossless path.
- An explicit Phase 6 sort overrides relevance order within the retrieved candidate window before display pagination. Keep the retrieval cap visible; sorting these candidates by size/date is not a global size/date order over all possible semantic matches. Plain metadata/name/content searches follow Phase 6 matching and sorting without semantic fusion. Both positive and negated date constraints exclude unknown timestamps.
- Use provisional cosine floors of **0.72 text, 0.65 image, and 0.64 audio**, with explicit user overrides retained. The original 0.25 baseline admitted every no-match query in the frozen generated evaluation. Joint calibration over the declared calibration splits of the generated and real-file corpora lowers only the image cutoff from 0.68 to 0.65. With weaker partial-keyword fusion, production-ranking replays retain all 72 generated positives with 2/32 negatives, and retrieve 66/70 real-file positives with 3/32 negatives. The real-file validation split alone still admits 3/12 negatives, and video descriptions reuse only two independent clips; these remain disclosed limits of the small evaluation. See `differences_from_phase_6_plan.md` for the evaluation scope and limitations. Treat it as a tunable relevance cutoff, not a probability or universal quality claim. The retrieval gate must check positive and no-match queries per modality; adjust the per-modality floors if fixtures show systematic misses/noise. Store those settings independently of vector provenance because changing a ranking threshold does not require re-embedding.
- Known-stale content enters neither semantic ranking nor extracted-text FTS results. Show offline results is off by default; enabling it adds clearly labeled last-known results. Current filename matches for stale files can still appear using observed path metadata without claiming a content match. Report query scope, partial coverage, and pending indexing in a compact status line.

### 7. Similarity features and fingerprints

[Phase 6](docs/File%20Manager/plan.md#image-hash-sorting-and-audio-similarity) separately plans image dHash value sorting and Hamming-distance sorting against one explicitly selected reference. Those reuse existing guarded image analysis and do not require this embedding index. The version/color prefix in the current perceptual hash is not part of its 64-bit dHash distance. Keep this deterministic visual fingerprint metric distinct from semantic similarity.

General document/topic similarity, separate summary vectors, and clustering-specific re-embedding remain outside the initial semantic-search release. Preserve file/segment identities, modalities, and pipeline provenance so those can be added later. No global all-pairs matrix or duplicate-detection guarantee is implied by this search index.

#### Sample similarity and a future audio map

The intended audio feature is **finding similar-sounding samples for creative substitution**, leading to an interface like [XLN XO](https://www.xlnaudio.com/products/xo) or [Algonaut Atlas](https://algonaut.audio/). These are product references, not claims about their proprietary analysis algorithms. Song identification/Chromaprint is not part of this feature. This is a separately staged capability, not a new prerequisite for initial text/semantic search.

- **Representation:** begin evaluation with a deterministic DSP feature vector: log-mel/MFCC spectral shape, brightness/noisiness, onset/attack, decay/envelope, active duration, and pitch/harmonicity when reliable. [Essentia's descriptor documentation](https://essentia.upf.edu/documentation.html) is a technical reference, not a selected dependency. Preserve separate attack/body/tail summaries so transient character is not lost in a whole-file mean. Compare this baseline against a suitable audio encoder, the existing semantic encoder, and a weighted combination using listening judgments; choose the simplest approach that passes. A text-semantic model recognizing “snare” does not establish good nearest-neighbor ordering among snares.
- **Preprocessing and scope:** start with bounded short one-shots, each summarized by one fixed-size vector plus structured descriptors. This is a different representation from the 30-second semantic-search segment policy; do not pad a short hit to that policy by default or infer long-file support. Version sample-rate handling, channel/phase policy, leading/trailing silence detection, feature scaling, and distance weights. Retain stereo information where useful; avoid destructive mono cancellation. Reduce sensitivity to arbitrary gain/leading silence while preserving relative envelope, pitch, and decay. Silence, unreliable pitch, and unsupported duration have explicit states rather than fabricated zero features. Loops require later rhythm/tempo-aware evaluation; long recordings need region-based representations.
- **Ranking:** support a chosen reference sample and nearest neighbors inside explicit folder/library scope, with duration/category filters. Normalize descriptor blocks and calibrate weights so an arbitrary numeric scale cannot dominate distance; do not concatenate raw descriptors and semantic vectors without calibration. Fit/version scaling independently of the visible folder, so merely changing the view does not change the metric. Treat low-confidence drum categories as optional filters, not mandatory partitions that hide useful neighbors. Keep file names out of acoustic features. Existing preview summaries can be reused only if their resolution and provenance meet this pipeline's needs.
- **Storage and updates:** share the index's file identity/revision, guarded decode, job cancellation, and freshness machinery. Cache sample-analysis records under their own pipeline/metric identity; do not mix these vectors with semantic vectors or require a second database. One short sample normally needs one searchable vector, even if its construction summarizes several time regions. Determine dimension/precision from quality measurements. Changed samples reanalyze individually; moves retain compatible analysis under the existing identity rules. Store map coordinates/layout version separately so filters, map rebuilding, or changes to projection parameters never force source decoding or embedding regeneration.
- **Map:** first ship reference-based ranked audition; later add a zoomable 2D layout, audition, and drag-out using shared playback/file-reference mechanisms. Evaluate a neighborhood-preserving projection such as [UMAP](https://umap-learn.readthedocs.io/en/latest/), without making it a runtime choice yet. Compute neighbors in the original feature space: screen distances and apparent clusters are an approximate visualization. Persist positions and projection/seed metadata; place additions using a compatible transform or anchored layout, and make global rearrangement an explicit rebuild. Index changes can retire points or update source status without automatic full-map refits. Use bounded neighbor search rather than retaining a quadratic distance matrix for a large library.
- **Acceptance:** use a representative sample library and listener-ranked alternatives, including subtle snare/kick variations, acoustic/electronic percussion, tonal hits, and effects. Compare DSP/model/hybrid neighbor usefulness and latency, not just broad category accuracy. Test gain changes, leading silence, encoding/sample-rate changes, stereo cancellation, silence, and short transients; retain distinctions for pitch, envelope, and texture where listeners value them. Exercise incremental additions/edits/moves, stale results, and stable map positions. Choose the feature/encoder recipe after this gate; implementation and any separate model download remain later work.

## Validation and milestones

The first milestone verifies the chosen implementation path; it is not a new open-ended database/runtime selection exercise. Performance values below are acceptance targets on the 3090 workstation with a warm local index, not current measurements:

- At 150,000 stored vectors, target p95 lexical results within 100 ms and warm hybrid results within 500 ms; CPU fallback targets two seconds for warm hybrid results. Measure cold load separately. Scope streaming above the memory cap must remain cancellable and report progress, even if it misses warm-cache targets. The pending-search status polls one request-tagged atomic count of checked indexed parts; the scan replaces it every 2,048 SQL-admitted segment references and at its final partial batch. This is a count, not a total/percentage or unique-file count. Stale/completed requests cannot supply the visible count, and the counter does not change eligibility, scoring or result limits.
- Assemble at least 60 positive queries (12 each for text, PDF, images, audio, and video), plus 20 no-match queries and 10 exact filename/identifier queries. Include brief relevant passages/events in long files and unrelated large files to expose segment-count bias. Agree expected files/locations from fixtures before tuning.
- Require at least 90% Recall@10 across positive queries and at least 80% in each modality, every exact filename query ranked in the promised exact-match tier, and no more than 20% of negative queries producing a semantic-only result above the configured floor. These are initial product gates; report failures and revise preprocessing/thresholds transparently instead of silently weakening the fixture set.
- On a representative subset, Q8 retrieval should lose no more than five percentage points of Recall@10 against the BF16 reference, and float16 vector storage no more than one percentage point against float32 scoring/storage. Also reject nonfinite/wrong-dimension outputs. Report sample size and ranking changes; high vector cosine agreement alone is insufficient.
- The production quality runner now includes a test-only matched f32 working-representation oracle over the same SQLite admission, Rust scorer and rank fusion. Use `scripts/search_quality_ranking.py --require-targets` with current library tests to check storage recall loss, changed rankings and exact-name tiers. The frozen synthetic corpus passes that storage comparison. The separate matched Q8/BF16 driver (`scripts/search_model_precision.py`) also passes the declared real-file corpus check on the 3090 with identical request hashes/device and checksum-verified weights: both models retrieve 66/70 positives, with 3/32 versus 2/32 negative-query results and zero measured storage/weight recall loss. Current reports are retained under `.fitness/evidence/phase6-quality-refresh-20261031/`. This small fixed corpus does not establish general quality equivalence: video diversity is only two independent clips, Q8 validation-only negatives are 3/12, and broader long-media coverage remains in the acceptance audit.
- Correctness gates require no deletion from incomplete scans, no publication from obsolete source/query generations, no stale semantic matches presented as current, and no generic content reads of protected interfaces. Cover source replacement, preserved mtime, hard links, remounts, root overlap/removal, offline return, and byte-non-UTF-8 paths. Exercise UI acceptance only in the private Weston/Niri runner.

1. **Storage/runtime and retrieval baseline:** measure the Q8 runtime on the 3090 and CPU fallback; confirm text/image/audio paths, effective context limits, output validity, and vector storage. Benchmark local SQLite plus exact similarity scanning at representative segment counts. Establish the retrieval fixture set and verify the Recall-derived shim against its pinned reference vectors; record adapted-source provenance.
2. **Text vertical slice:** implement file/path/segment records, passage extraction, FTS and semantic retrieval, transactional publication, and startup reconciliation. Include replacement-at-same-path, rename, hard-link, incomplete-scan, and stale-revision cases from this first slice.
3. **Media coverage:** add image, PDF, audio, and video support incrementally. Evaluate retrieval of brief passages/events within long files, segment counts, sampling omissions, and page/time explanations. Measure multimodal ranking rather than extrapolating text results.
4. **Continuous freshness and UX:** integrate the shared Phase 6 parser and `emb` mode, then add runtime monitoring, remote reconciliation policy, query prioritization, coverage/error reporting, and cancellation. Exercise disconnect/reconnect, permission changes, notification loss, cancelled crawls, model failures, and edits during extraction.
5. **Operational verification:** validate resumability, schema/pipeline upgrades, index backup/recovery, root cleanup, memory bounds, and warm/cold latency. Compare BF16 reference retrieval on selected fixtures before accepting the quantized pipeline.

Deletion and stale-publication correctness are requirements of the first indexing slice, not polish deferred until the end. Implementation is in progress. The milestones above define the validation scope; consult [the implementation ledger](differences_from_phase_6_plan.md) for completed checks, measured deviations and outstanding gates.
